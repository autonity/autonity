# Protocol Contract Upgrade Guide

This guide explicates the process for developing and deploying a protocol contract upgrade.

It is divided into two sections, one for the upgrade developer and one for the network operator.

## Developer guide

1. Develop the contract upgrade under the proper folder (`autonity/solidity/contracts/upgrades/n`), 
   where `n` is the first available **upgrade number**. The contract **filename** and **name** MUST 
   be suffixed by the **upgrade number**. 
   - Example: upgrade number `0` for `Oracle.sol` is stored in the file `upgrades/0/Oracle0.sol`. The contract
   name is `Oracle0`.
2. (optional) add the upgrade contract to `bindings.sol` if auto-generated bindings are needed.
3. add a call to `gen-contract` for the new upgrade under the `compile-contracts-upgrades` Makefile target. This
    will allow for contract compilation and generate the `.go` files with embedded bytecode.
4. Insert the new upgrade in the `Upgrades` list in `autonity/upgrades.go`. Every upgrade is characterized by the 
   following fields:
    - `Name`, a short name for the upgrade.
    - `Description`, a more long form description of the upgrade.
    - `ExclusionList`, a list of chainIDs where the upgrade should not be deployed at genesis. This will normally
    include all the networks which are already running at the time the upgrade is deployed.
    - `Upgrades`, all the individual contract upgrades which collectively constitute the protocol upgrade. Every contract
      upgrade is characterized by the following fields:
      - `Target`, the address of the contract to be upgraded.
      - `Abi`, the upgraded ABI (it is auto-generated by `gen-contract` under the `generated` package).
      - `Bytecode`, the upgraded bytecode (it is auto-generated by `gen-contract` under the `generated` package).
      - `Hash`, the upgraded code hash (it is auto-generated by `gen-contract` under the `generated` package).
      - `Args`, the arguments for the upgraded contract constructor (can be `nil` if there are no arguments).
      - `VersionString`, a semver version string. Please follow the rules of [semantic versioning](https://semver.org/).
      - `BaseCode`, the code of the non-upgraded contract (use `go:embed` directives to embed source files into strings).
      - `UpgradedCode`, the code of the upgraded contract (use `go:embed` directives to embed source files into strings).

<div style="background-color: #fff3cd; border: 1px solid #ffeeba; padding: 10px; border-radius: 5px; color: #856404;">
  <strong>Warning:</strong> make sure that the exclusion list for the upgrade is properly filled with all the network on 
    which the upgrade will be executed via operator transaction. 
</div>

## Operator guide

1. Clone the [autonity repo](https://github.com/autonity/autonity), or pull the latest changes from the `develop` branch.
2. Run `make upcheck` to build the `upcheck` tool. This tool will help you inspect the upgrade and generate the calldata
   for the upgrade transaction. The tool will be built under the `build/bin` folder.
3. List the available upgrades with `upcheck list`. Example output:
    ```terminaloutput
    upgrade 0       Oracle Contract slashing bugfix
    upgrade 1       UpgradeManager contract new features
    ```
4. Inspect the details of the upgrade to be deployed (`n`) with `upcheck detail <n>`. Example output:
    ```terminaloutput
    upgrade 0       Oracle Contract slashing bugfix
    description     The `slash()` function was incorrectly called, passing the oracle address
                    instead of the node address of the offender. This was causing a revert in the
                    `getValidator()` function in the autonity contract when trying to do the actual
                    slashing.
    excluded        [65000000 65010004]

    upgraded contracts (1)
            OracleContract
                    address 0x47e9Fbef8C83A1714F1951F142132E6e90F5fa5D
                    hash    0xce27bc56daf1840ff5902958bae5b95183310ce92e616be054b230771f17e8e6
                    version
    ```
5. **IMPORTANT**: The `detail` sub-command can also be used to inspect the source code difference between the base contract and the upgraded one. 
   append the `--show-source` flag to see the diff.
6. Once you are satisfied, assemble the calldata for the upgrade transaction using `upcheck assemble <n>`, where `n` is the upgrade
   number of the upgrade to be deployed.
7. Insert the generated calldata into the data field of the upgrade transaction, and proceed to the signature process.

<div style="background-color: #fff3cd; border: 1px solid #ffeeba; padding: 10px; border-radius: 5px; color: #856404;">
  <strong>Warning:</strong> the "assemble" sub-command returns the <b>calldata</b> of the upgraded transaction encoded
  in a hexadecimal string. This is <b>NOT</b> the full transaction encoded, but rather just the data payload. All the 
  other transaction fields (e.g. to, gaslimit, gasprice) are left for the operator to fill.
</div>
